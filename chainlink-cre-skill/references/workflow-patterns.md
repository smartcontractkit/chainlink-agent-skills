# Workflow Patterns

Use for the trigger/callback model, generated configuration, secrets, DON Time, randomness, and handler composition. Capability-specific examples live in their references.

## Canonical handler model

A workflow registers one or more trigger/callback pairs. Every complete TypeScript example returns each `handler(...)` registration from a local `initWorkflow` and includes an executable `main` that creates `Runner` and runs it; never discard handler definitions or import/call an SDK `initWorkflow`. This file owns the base cron registration examples.

CRE cron schedules emitted in source, target config JSON, workflow records, docs, or commands must contain exactly six fields: seconds, minutes, hours, day of month, month, and day of week. Use `0 */5 * * * *` for every five minutes. Normalize a user-supplied five-field schedule by prepending `0` when that preserves its meaning; otherwise reject it clearly rather than emitting five fields.

```typescript
import { CronCapability, Runner, handler, type Runtime } from '@chainlink/cre-sdk'

type Config = { schedule: string }
const onCronTrigger = (runtime: Runtime<Config>): string => {
  runtime.log(`Triggered at ${runtime.now().toISOString()}`)
  return 'done'
}
const initWorkflow = (config: Config) => [
  handler(new CronCapability().trigger({ schedule: config.schedule }), onCronTrigger),
]
export async function main() {
  const runner = await Runner.newRunner<Config>()
  await runner.run(initWorkflow)
}
```

Go's canonical registration is `cre.Handler(cron.Trigger(&cron.Config{Schedule: config.Schedule}), onCronTrigger)` inside the `cre.Workflow[*Config]` returned by `InitWorkflow`, with the WASI entry point wired in `main`:

```go
package main

import (
	"log/slog"

	"github.com/smartcontractkit/cre-sdk-go/capabilities/scheduler/cron"
	"github.com/smartcontractkit/cre-sdk-go/cre"
	"github.com/smartcontractkit/cre-sdk-go/cre/wasm"
)

type Config struct {
	Schedule string
}

func onCronTrigger(config *Config, runtime cre.Runtime, payload *cron.Payload) (string, error) {
	runtime.Logger().Info("triggered", "time", runtime.Now().String())
	return "done", nil
}

func InitWorkflow(config *Config, _ *slog.Logger, _ cre.SecretsProvider) (cre.Workflow[*Config], error) {
	return cre.Workflow[*Config]{
		cre.Handler(cron.Trigger(&cron.Config{Schedule: config.Schedule}), onCronTrigger),
	}, nil
}

func main() {
	wasm.NewRunner(cre.ParseJSON[Config]).Run(InitWorkflow)
}
```

The callback shape is `func onCronTrigger(config *Config, runtime cre.Runtime, payload *cron.Payload) (Output, error)`. Keep the entry style generated by the selected template: define/export `main` and wire its Runner exactly as shown, calling `main()` explicitly only when that template's entry point expects it. HTTP trigger imports add `github.com/smartcontractkit/cre-sdk-go/capabilities/networking/http` (the same package as the HTTP client — there is no separate webhook-trigger package); add `github.com/smartcontractkit/cre-sdk-go/capabilities/blockchain/evm` (and its `bindings` subpackage when using generated contract bindings) for EVM triggers/reads/writes — see [triggers.md](triggers.md) and [evm-client.md](evm-client.md) for those complete examples. Import only the packages the workflow actually calls; an unused import fails compilation.

For shared config/secrets/consumer state, register several handlers in one `initWorkflow`/`InitWorkflow` and instantiate each capability once. Separate workflows only for independent chains/config, lifecycle, secret namespaces, or consumer ownership. A request combining cron and HTTP/webhook behavior must follow the single complete dual-handler TypeScript path in [triggers.md](triggers.md), including imports, config and payload types, defined callbacks, both registrations, local `initWorkflow`, `Runner`/`main`, `runtime.now()` for time, and serialized string returns; trigger names or registration fragments are not an answer.

## Generated configuration

`cre init` creates these owners; edit generated files rather than reconstructing them:

| File | Purpose |
|---|---|
| root `project.yaml` | target-wide EVM selector/RPC settings |
| workflow `workflow.yaml` | per-target workflow name, entry, config, and secrets paths |
| target config JSON | values exposed as `runtime.config` (TS) or handler config (Go) |
| root `secrets.yaml` | workflow secret IDs mapped to environment-variable names |

When a secrets/config scaffold is requested, show the concrete root `project.yaml`, workflow `workflow.yaml` entry (including the target `config-path`), target config JSON such as `config.staging.json`, root `secrets.yaml`, and `.gitignore`. Include `cre secrets list --target <target>` and route any create/update command through [operations.md](operations.md).

Example shape, not a project scaffold:

```yaml
# secrets.yaml: IDs and environment references only
secretsNames:
  MY_API_KEY: MY_API_KEY_VAR
```

```yaml
# workflow.yaml: the built-in templates generate at least two top-level targets
staging-settings:
  user-workflow:
    workflow-name: my-workflow-staging
  workflow-artifacts:
    workflow-path: ./main.ts
    config-path: ./config.staging.json
    secrets-path: ../secrets.yaml
production:
  user-workflow:
    workflow-name: my-workflow-production
  workflow-artifacts:
    workflow-path: ./main.ts
    config-path: ./config.production.json
    secrets-path: ../secrets.yaml
```

Preserve target names and the meaning of all user-specified schedules, plus all units, decimals, selectors, addresses, resource IDs, and secret names across code/config/docs/simulation. Normalize every five-field cron schedule to the equivalent six-field CRE form by prepending `0`, or reject it clearly if normalization is unsafe; this applies equally to target config JSON and workflow records. A target config JSON block must be strictly valid JSON: never put a `//` or `#` comment inside the fenced block — label the file's path in the prose sentence that introduces it — and it must include every field the declared TypeScript `Config` type or Go `Config` struct reads (a config that omits a field the handler uses, such as `schedule`, is not a runnable workflow). When more than one target shares an invariant, that field's value must match across every target's config file, not only the one shown first.

### Receiver-free local simulation config

For a handler-0 simulation before its receiver exists, model configuration as two closed variants and validate it with the runner's Standard Schema:

```typescript
type Config =
  | { mode: 'local-simulation'; samplePreviousPrice: string; receiver?: never }
  | { mode: 'production'; receiver: string; samplePreviousPrice?: never }
```

Add the prompt's shared endpoints, schedule, decimals, threshold, and other fields to both variants. Reject unknown modes, a receiver in the local variant, and `samplePreviousPrice` in the production variant. The sample must pass the same strict decimal syntax, scaling, sign/range, and `bigint` overflow checks as fetched prices.

Use this canonical positive-decimal-to-E8 conversion for fetched prices and `samplePreviousPrice`; never derive padding from the full string length or the decimal point's absolute index:

```typescript
const UINT256_MAX = (1n << 256n) - 1n
const E8 = 100_000_000n

function parsePositiveDecimalE8(value: string): bigint {
  const match = /^(0|[1-9]\d*)(?:\.(\d{1,8}))?$/.exec(value)
  if (!match) {
    throw new Error('price must be a positive base-10 decimal with at most 8 fractional digits')
  }

  const [, whole, fraction = ''] = match
  const fractionE8 = fraction.padEnd(8, '0')
  const scaled = BigInt(whole) * E8 + BigInt(fractionE8)
  if (scaled <= 0n || scaled > UINT256_MAX) {
    throw new Error('scaled price is outside uint256 bounds')
  }
  return scaled
}
```

The input grammar accepts at most eight fractional digits, then pads that captured fraction to eight digits: `3500.12345678` becomes `350012345678n`. It rejects over-precision rather than rounding or truncating, along with signs, exponent notation, whitespace, leading-zero integers, missing whole/fractional digits, zero, and uint256 overflow. Generated local tests must include a focused assertion that `parsePositiveDecimalE8('3500.123456789')` throws.

Do not put the branch at the top of handler 0. First run the normal real HTTP capability requests, response/status checks, decimal conversion, bounds checks, and consensus aggregation. Then:

- `local-simulation`: compare the consensus price with the validated and scaled sample previous price, run the normal changed-price/threshold decision, log and return a result explicitly labeled `local-simulation`, and stop before receiver validation, CRE report creation, `EVMClient` construction, or Forwarder delivery.
- `production`: validate the configured receiver as a well-formed nonzero address, obtain the real previous value when required, run the changed-price decision, create the CRE report and deliver it through the Forwarder when a write is due, and fail closed on every validation, capability, report, delivery, or missing-transaction-hash error.

Never inject fixture observations into the local branch: it exists to exercise the handler's actual HTTP and consensus path through `cre workflow simulate`. Never deploy or broadcast a config with `mode: "local-simulation"`; those commands must select a production target. The early return must also make an accidentally broadcast local invocation incapable of constructing or sending a transaction. See [simulation.md](simulation.md) for the exact handler-0 command and [project-scaffolding.md](project-scaffolding.md) for the matching local/private target.

## Secret APIs

Simulation values come from an environment or `.env` consumed by the CLI; deployed values come from Vault DON. `secrets.yaml` stores no value. Lifecycle commands and custody rules are in [operations.md](operations.md).

For an ordinary authenticated API request, default to the root `secrets.yaml` ID-to-environment mapping, resolve the value in DON mode with `runtime.getSecret({ id: 'MY_API_KEY' }).result().value`, and pass that value into the regular authenticated HTTP capability request. Do not replace this path with a raw Vault placeholder such as `{{.MY_API_KEY}}`, `vaultDonSecrets`, Confidential HTTP, or a TEE pattern unless the user explicitly requests Confidential HTTP, request-level confidentiality, or TEE execution.

TypeScript is synchronous and object-shaped:

```typescript
const value = runtime.getSecret({ id: 'MY_API_KEY' }).result().value
const values = runtime.getSecrets([{ id: 'KEY_A' }, { id: 'KEY_B' }]).result()
```

Never `await` or pass a bare string. Missing or unauthorized secret resolution fails; catch it only when the workflow has a real fallback. `TeeRuntime` has the same API. `NodeRuntime` has no secret provider; fetch in DON mode and pass the value as an argument to `runInNodeMode`.

Go:

```go
secret, err := runtime.GetSecret(&cre.SecretRequest{Id: "MY_API_KEY"}).Await()
```

`secret.Value` is the value. Batch with `GetSecrets([]*cre.SecretRequest{...}).Await()`. When a secret feeds an external HTTP call, resolve the secret in DON mode *before* entering node mode (`NodeRuntime`/Go node context has no secret provider) and pass the resolved value as an argument into `runInNodeMode`/`RunInNodeMode`, which itself must carry a consensus aggregator — never skip aggregation because the call is secret-backed; see [http-client.md](http-client.md).

An end-to-end API-key example must actually pass the resolved value into an authenticated capability request; retrieval followed only by a comment or unused value is incomplete. A requested full deployed-secret lifecycle must include list, create, update, and delete, plus the Early Access, login, linked-funded-wallet, uploaded-secret, simulation, permanence, and confirmation requirements owned by [operations.md](operations.md).

### CRE CLI v1.1.0 secret-name substring bug

Resolution can fail with `secret not found` when the environment-variable name is a substring/prefix of the secret ID, for example `GEMINI_API_KEY` for `GEMINI_API_KEY_SECRET`. Use a non-overlapping environment name such as `GEMINI_API_KEY_VAR`:

```yaml
secretsNames:
  GEMINI_API_KEY_SECRET: GEMINI_API_KEY_VAR
```

## DON Time and randomness

Use `runtime.now()` (TypeScript) or `runtime.Now()` (Go), never `Date.now()`, `new Date()`, `time.Now()`, or other system clocks in DON mode. DON Time is a consensus median with limited resolution; do not depend on sub-second precision.

Go randomness must come from `runtime.Rand()`:

```go
source, err := runtime.Rand()
if err != nil { return nil, err }
small := source.Intn(100)
large := new(big.Int).Rand(source, new(big.Int).SetUint64(1_000_000))
```

Never use global `math/rand` or `crypto/rand` in DON mode. TypeScript has no runtime randomness API.

## Capability completion

TypeScript capability/secret/report calls return lazy handles resolved with `.result()`; they are not JavaScript promises:

```typescript
const response = httpClient.sendRequest(runtime, fetchFn, aggregation)(url).result()
const call = evmClient.callContract(runtime, options).result()
const report = runtime.report(prepareReportRequest(encoded)).result()
```

Go capability calls return `cre.Promise[T]`; `.Await()` returns `(T, error)` and drives the single-threaded event loop.

For TypeScript config validation, pass a Standard Schema such as Zod to `Runner.newRunner({ configSchema })`.

## Generation checks

- Return requested workflow code, concrete configuration, supporting contract/interface, and commands themselves; never substitute a completion summary or unverified claim that they ran.
- Default to TypeScript only when prompt/repository does not indicate Go.
- Use `cre init` after reading scaffolding; do not fabricate project files.
- Use regular HTTP unless request-level confidentiality is required; whole-handler confidentiality is a separate TEE capability.
- Aggregate external/node-mode results; use scaled integers/decimal strings for business values and `bigint` for Solidity integers.
- For every generated local price workflow, include and run a focused parser test that accepts `3500.12345678` as `350012345678n` and rejects the over-precision input `3500.123456789`.
- Convert `bigint` to string before `JSON.stringify`.
- Include the minimal consumer/ABI/interface/relay/mock boundary needed for a coherent integration.
- Read simulation before providing its command and always include `--target`.
